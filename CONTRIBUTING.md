# Contributing

Thanks for helping with the React Native Screens docs.

## Local setup

```bash
yarn install
yarn start
```

`yarn start` runs Docusaurus in dev mode at `http://localhost:3000/react-native-screens-docs/` with this checkout's `docs/` only, unless `yarn docs:assemble` has added the other versions (see [Previewing every version](#previewing-every-version)). `yarn build` produces a production bundle in `build/`.

## Documentation structure

- `docs/` — this branch's version. On `main` it is the unreleased version, `next`; on a version branch (`5.x`) it is that version.
- `sidebars.js` — manual sidebar that mirrors the IA. Update it whenever you add or rename a page.
- `docs/**/api-reference/` and `api-reference.lock.json` — generated by `yarn gen:api` from the library; never edited by hand.
- `version-map.json` — the published versions; only `main`'s copy is used.

## Pull requests

- Branch off `main`, or off the version branch for a change to a released version (see [Versions](#versions)).
- Fill out the PR template, including the related react-native-screens PR if the docs change follows a source change.

## Versions

Every version of the docs is a branch: `main` is `next`, the unreleased version, and each release line has its own branch (`5.x`, …). A version branch is cut from `main`, and only its content counts: `docs/`, `sidebars.js`, `api-reference.lock.json` and `static/`. The site is built from `main`'s code with every version's content (`yarn docs:assemble`), and each version is served under its own path: `/docs/5.x/…`, `/docs/next/…`. In the built site, `/docs/…` without a version redirects to the same page of the latest version.

`version-map.json` on `main` lists the published versions. `current` is `next`'s `label` and `banner`. `versions`, newest first, gives each released version's `name` (its URL path; lowercase, not `current` or `next`), `branch`, `label` and `banner` (`none`, `unreleased` or `unmaintained`). `latest` names the version the site opens on; it is never `next`. A mistake in the file fails the build.

Publishing is `.github/workflows/docs-publish.yml`: every push to `main` or to a branch whose name ends in `.x` builds and deploys the whole site, so a version branch's name must end in `.x`. Pull requests are built the same way without deploying: one to `main` with its own code and every version from its branch, one to a version branch as that version, with `main`'s code. A run that fails publishes nothing and the site stays as it was; fix the cause named in the log and push, or re-run **docs publish** from the Actions tab. A push made with `GITHUB_TOKEN`, such as a bot's merge, starts no workflow: run **docs publish** by hand (with `dry_run` to list what would change on `gh-pages`).

While `version-map.json` lists a version whose branch does not exist, every publish fails, and pull requests check that version with their own `docs/` (the run shows a notice); push the branch to fix it. A version branch not yet in the map is not published: pushes to it publish the site without it.

### Previewing every version

From a checkout of `main` or a branch off it (a version branch has older code and an outdated `version-map.json`):

```bash
git fetch origin
yarn docs:assemble                         # every version from origin/<branch>
yarn docs:assemble --dir 5.x=../docs-5.x   # 5.x from a local checkout, uncommitted changes included
yarn docs:assemble --ref 5.x=<ref>         # 5.x from another commit, tag or branch
yarn start                                 # or yarn build && yarn serve, which also has the /docs/… redirects
yarn docs:assemble --clean                 # back to this checkout's docs/ alone
```

Run `yarn docs:assemble` again after `version-map.json` changes; the build stops until you do.

### Updating a version

1. Branch off the version branch, e.g. `5.x`.
2. Bring the changes. Only the version's content counts on its branch; the site runs `main`'s code. Cherry-pick hand-written content from `main`; for a new release of the library, regenerate the API reference with `yarn gen:api --ref <tag>` rather than cherry-picking generated files.
3. Check it with `main`'s code: in a checkout of `main`, `yarn docs:assemble --dir 5.x=<your checkout>`, then `yarn build`.
4. Open a pull request to the version branch. Merging it publishes the site with the change.

### Cutting a version

1. Cut the branch from `main` and push it; its name must end in `.x`:
   ```bash
   git fetch origin
   git switch -c 6.x origin/main
   git push -u origin 6.x
   ```
   If `api-reference.lock.json` records a later library commit than the release, run `yarn gen:api --ref <release tag>` and commit before pushing. Until step 2 is merged, pushes to `6.x` publish the site without it.
2. Open a pull request to `main` that adds the version to `version-map.json` as the first entry of `versions` and makes it `latest`:
   ```json
   { "name": "6.x", "branch": "6.x", "label": "6.x", "banner": "none" }
   ```
   Give the previous version `"banner": "unmaintained"` once it is no longer maintained. Until the branch is pushed, the pull request checks the version with its own `docs/` (a notice says so); merged, it makes every publish fail until the branch exists.
3. Merging it publishes the new version.

### Retiring a version

In a pull request to `main`, give it `"banner": "unmaintained"`. Removing it from `version-map.json` instead removes its pages from the site with no redirect, so links to them break; keep its branch either way.

### Rules that keep every version building

- A version's `name` is in its URLs, so it never changes.
- `main`'s code renders every version's pages. What their MDX relies on — `ReferenceHeading`, `CollapsibleDeclaration` and the other MDX components, `@site/` and `@theme/` imports, the format of `api-reference.lock.json` — can gain features but must not change or lose ones a version uses. The navbar and home page link to `react/containers/stack/index`, so the latest version must have it. Pull requests to `main` build every version, so a break shows there.
- `static/` on `main` is served for every version, so changing a file there changes it for every version that uses it; add a changed file under a new name. A file only a version has is served from its branch; two versions with different files at the same path fail the build.
- A broken link in any version fails every build, `main`'s included.
- A version branch runs its own copy of `docs-publish.yml`'s steps, with `main`'s scripts. A change to the steps reaches a version branch only when it is copied there.

## Recording conventions

Screen recordings demonstrate components. Keep them small, silent, and consistent.

### ffmpeg compression

Run every recording through:

```bash
ffmpeg -i input.mov \
  -vf "scale=600:-2,fps=30" \
  -c:v libx264 -crf 28 -preset slow \
  -movflags +faststart -an \
  output.mov
```

### Constraints

- Max 500 KB per file
- Max 10 seconds
- No audio (`-an`)
- H.264 baseline profile

### Light/dark variants

If a feature renders differently across color schemes, ship both:

- `featureName_light.mov`
- `featureName_dark.mov`

Store recordings under `static/recordings/`.
